## 2. つなぎ方の設計

### 2-1. 形: 「会話×案件×出来事の時系列」

1本の物として引けるように、**2つだけ**新しく置く（どちらも動的データ）。

| 置く物 | 種類 | 中身 | なぜ新しく要るか |
|---|---|---|---|
| `deal_outcomes`（結果の表） | **正の記録**（新しい事実） | 会話×案件（エピソード）ごとに1行: 到達した段階（初回／条件／物件送付／内覧／申込／審査／成約）と各時刻・**最終の結果**（成約／失注／進行中）・結果の確かさ（確定／推定）・**決まった（落ちた）物件**の building_key と号室・失注の型と理由・根拠の行の id | 結果はどこにも無い（B）か推定（A）。結果だけは今から残さないと二度と取れない |
| `outcome_events`（出来事の台帳） | **派生**（毎日作り直せる） | 既存の表から決定論で集めた出来事: ブレインの判断・送った AIX・返信・送った物件・お客様の反応・見積・内覧の予定/実施・申込・審査の変化・成約/失注。列は 会話・時刻・種類・building_key・号室・元の表と id・案件の番号 | 物件の照合（buildingKeyOf）が SQL ではできないので TS で揃えて置く。元の表が正・こちらは**消しても作り直せる** |

- ビューだけで済ませない理由: 物件の名前の照合（F）と案件の区切り（否決→切り替えで新しい案件）が TS の純関数でしか正しく出せない。逆に、元の表をまたいだ「全部の出来事」を新しい正の表に写すことはしない（二重に持たない）。
- **案件（エピソード）**: 1つの会話でも、審査に落ちて切り替えたら新しい案件（stage_history の 申込→提案中・status_manual_back_at・否決の文）。成約・失注は案件ごとに付く。
- **列の名前の注意**: brain_decision_logs.outcome は「判断の後にスタッフが何をしたか」なので、結果は別の名前（deal_outcome・result）にする。
- 静的な物（段階の順・失注の型・理由の選択肢・期限の日数）はコードに固定（`app/lib/deal-outcome.ts`）。DB に置かない。

### 2-3. 成約・失注の定義（案・竹内さんに決めてもらう）

**成約**
| 確かさ | 条件 | 今の数 |
|---|---|---|
| 確定 | スタッフが成約にした／申込のツールの同期で成約・契約になった | 19 |
| 推定 | 申込中で14日やり取りなし（今の auto-seiyaku） | 26 |
→ auto-seiyaku は止めずに、**確かさ「推定」の印を付けて**台帳に入れる案。学習・ブレイン・実績の数字には確定だけを使う。

**失注（型はコードに固定）**
| 型 | 取り方 | 確かさ |
|---|---|---|
| L1 他で決めた・辞退 | お客様の文（tpo-hint の DECLINE_RE と同じ語） | 確定 |
| L2 ブロック | line_status = unfollowed | 確定 |
| L3 無反応 | 申込前で、お客様の最後の発言から **N日**（案 30日）・こちらの追いかけの後も返事なし | 推定（返事が来たら取り消して進行中に戻す） |
| L4 引越し中止・延期 | 文（「引越しやめ」「延期」「更新することに」）＋ DeepSeek | 文で決まった物は確定 |
| L5 審査落ちの後の離脱 | 否決→切り替えの後に L1〜L3 | 型に「審査の後」を付ける |
| L6 申込の取り消し | 申込→戻した＋取り消しの文 | 確定 |

**失注の理由（選択肢を固定）**: 他社で決定／合う物件が無い（条件）／費用／時期が延びた／引越し中止／審査／連絡が途絶えた／不明。
- 決定論で取れる: L1・L2・L3・L5・L6 の型、「他社」「審査」「連絡途絶」。
- DeepSeek で読む: 型は分かったが理由が文の中にある時だけ（L1・L4 の最後の数通）。**申込中の文は渡さない**（deepseek_cutoff_at・project_post_apply_out_of_scope）。渡すのは申込前の最後のお客様の発言 3〜5通だけ・名前は伏せる。

### 2-4. 申込以降の線

- 申込以降は別ツールの領分。こちらは**結果だけ受け取る**: 申込（段階の変化）／審査中／否決（戻した印・否決の文）／成約（同期・手）。
- 今は段階の変化（sync-from-screening の状態名・手の変更・auto-seiyaku）で受ける。いずれ申込のツール側から「審査の可否・成約日・物件」を受ける口（webhook の列を足す）にする時は、**screening-admin のコードは触らない**ので、向こうが送ってくる値を受ける形をこちらで用意して待つ（DB の webhook の設定変更だけで済む形が理想）。
- 申込中の文（申込フォーマット・本人確認・勤務先）は台帳に**写さない**。台帳は出来事の種類・時刻・物件・id だけ。

### 2-5. ブレインの側で残すべき項目（実物で確かめた）

ブレインの判断は brain-core → `brain_decision_logs`（1判断1行）と `conversations.suggested_aix_meta`（最新の1つ・上書き）に残る。
今の行に有る物: 時刻・提案の AIX（suggested_action）・check_pattern・reply_mode・next_steps・enforcement_level・状態・decision_source（llm／promise:pickup／guard:first_contact／signal:*／rule:*…）・analysis_mode・読んだ発言の時刻・場面の根拠・digest（intent・concern・感情・aix・**物件 prop（文字40字）**・**買う気配 sig**・方向・時期・ずれ shift）。

| 足りない物 | 今どこにあるか | 足す先（案） | 理由 |
|---|---|---|---|
| 判断した物件の **building_key・号室** | digest.prop の文字だけ | brain_decision_logs に `building_key`・`room` | 物件ごとに「判断→結果」を結ぶ鍵（F） |
| two_choice（2択）・pending_pickup・checkpoint_stage・closing_strategy の要約 | suggested_aix_meta（上書き） | digest に短く足す（tc・pp・cp・cs） | 判断の時点の中身が後で消える（E） |
| 場面（brain-scene のキー） | line_watch_turns.scene_key（10/1〜・見張りだけ） | brain_decision_logs に `scene_key` | 場面ごとに「どの判断が成約につながったか」を出す |
| 確信度 | **無い** | LLM に数字を言わせない。代わりに決定論の「根拠の強さ」＝decision_source の種類＋enforcement_level＋sig を使う | LLM の確信度は当たらない・費用も増える |
| モデル・ブレインの版 | llm_usage_logs にはあるが判断の行に無い | `brain_version`（コミットの短い id か設定の指紋） | 版の前後で成約が変わったかを比べる |
| 判断→送った AIX／返信の対 | cron/brain-aix-eval が時刻で対にして outcome に書く | outcome_events を作る時に `decision_id` を付ける（aix_usage_logs・ai_reply_examples 側は変えない） | 既存の対付け（brain-outcome.ts）をそのまま使う |

- どれも LLM を足さない（今ある出力を残すだけ）。費用0。
- 新しい列は migrate-schema/route.ts と同時に足す（絶対ルール4）。
